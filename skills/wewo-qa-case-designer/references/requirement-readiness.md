# Requirement readiness and confirmation

This is a requirement-only gate before test design. It does not require a coverage plan, test-point tree or cases, and it does not certify that natural-language requirements are true or exhaustive.

## Three audits before the final summary

1. **Business coverage**: reread supplied sources and walk the complete relevant journey: goal/scope, actors/ownership, entry/prerequisites, actions, conditions/limits, object states, data changes, alternate/failure paths, downstream effects and observable acceptance. Check the inventory against the original document, including tables, notes and diagrams. Skip irrelevant dimensions with a reason; reopen material missing ones. Model independently defined status fields and entity lifecycles separately; confirm their relationships instead of inventing a single combined lifecycle.
2. **Branch expansion**: revisit every material answer and its consumers. Check whether the answer created a consequential rule or acceptance question that was never asked. Inspect shared rules across units, including unchanged pages. Reopen branches until resolved or explicitly outside the confirmed design scope. Do not expand hypothetical implementation internals.
3. **Decision provenance**: for every included rule, read its actual source clause or current user decision and verify condition, trigger and expected business outcome. A reference with the right ID but unrelated meaning fails this audit. Resolve conflicts using applicable source authority and actual owner decisions. AI recommendations, convenience and industry conventions cannot establish a product oracle. Check accepted exclusions and remaining restrictions explicitly.

Run these audits on the current understanding before displaying a final confirmation question. Findings return to the dialogue and business model; do not use the final confirmation request to hide unfinished decisions. Accepting an unresolved risk does not provide an expected result. Clarify the oracle or explicitly exclude that behavior from final scope and disclose the lost coverage.

## Private state contract

Context schema 1.4 adds the following to the source/rule model:

- `requirement_units`: canonical current understanding. Use `unreviewed`, `discussing`, `waiting`, `confirmed` or `excluded`. Preserve `id/title/source_refs/understanding/confirmed_facts`, plus `depends_on` (upstream unit IDs) and `rule_refs` (current included rules). Confirmed units have grounded facts/rules; excluded units have an `exclusion_reason` and no active rules. Confirmed means material facts are resolved, not final approval. Draft facts/rules may be empty.
- `open_questions`: `id`, `unit_id`, `description`, `impact`, `material`, optional `parent_decision_ref`. Record material branches even before the next question is displayed. Remove a resolved question from this current queue only after preserving the actual answer in event/decision history.
- `dialogue_events`: chronological actual visible exchanges, with stable `id`, `kind`, `text`, and `message_ref`. Save displayed options/recommendations and raw replies separately from interpretations. Module checkpoints are not final summary/confirmation events. A stored draft is not a visible exchange; follow the [record/resume procedure](progressive-dialogue.md#record-and-resume).
  - `question`: `question_ids` lists displayed IDs. For a follow-up to the same decision, `revisits` maps each repeated question ID to its latest earlier question event ID, for example `{"Q1.1":"EVT-QUESTION-001"}`. Changed wording/options belong in the new event; new decisions use new IDs.
  - `answer`: `in_reply_to` is one earlier question event ID, or an array when one actual reply addresses multiple batches. `question_ids` lists only questions actually addressed (including an explicit unknown), not every question asked. It is required for replies to multi-question batches; omission on a single-question reply means that question. Do not cite multiple versions of the same question in one reply; link the applicable occurrence. Preserve a reply once, even when several decisions use it.
  - `summary`: `snapshot_sha256` binds the displayed final requirements. `confirmation`: a single string `in_reply_to` identifies that summary. A correcting reply returns to discovery.
- `decisions`: retain unit/question references and parsed resolution, with `response_event_ref` pointing to the actual answer. Superseded decisions have `status=superseded` and `superseded_by`; retain them as history but never as active rule, extraction or point references. A current decision must use the latest relevant answer to the latest occurrence of its question. A renewed question or later correction leaves the old decision stale until reconciled. Current `assumed` business decisions block readiness; obtain confirmation or an explicit exclusion. An assumption explicitly accepted as the product rule becomes confirmed with that actual answer, not by bulk relabeling. Open answers need no `selected_options`.
- `branch_reviews`: one record per actual answer with `answer_event_ref`, impacted `unit_refs` and a substantive `note` identifying opened/eliminated branches, consequences and resulting questions. “Done” is not a branch review. Several questions in one reply share this review.
- `requirement_review`: `status=draft/ready`, current `snapshot_sha256`, and one `checks` record for each `business-coverage`, `branch-expansion`, `decision-provenance`, each with all current `unit_refs` and a substantive `note` describing the review and accepted scope limits. This is agent review evidence, not human approval.

Continue source extraction/rule modeling during discovery. `rules=[]`, `coverage=[]` and empty `design_models/factors` are valid draft values; do not fabricate coverage to obtain a requirement digest. Once designing coverage, supply all six applicability entries. `requirement_items` accounts for each included original segment and each *active* decision. When superseding a decision, retain its history and reconcile active extraction/rules and affected facts after resolving consequences.

## Gate order

1. Close material business questions and complete the three audits. Obtain `<qa-tool> requirement-digest <context>`; store it with the actual requirement review. Run `<qa-tool> validate-requirement-readiness <context>`. This checks recorded state and never writes an approval.
2. Present one consolidated summary understandable without private JSON: scope, actors, full flow, business rules, limits, states, permissions, cross-module effects, decisions and exclusions. Preserve this exact text as a `summary` event bound to the digest.
3. Ask for final confirmation. On an actual affirmative reply, preserve a `confirmation` event. Set `requirement_confirmation` with `status=confirmed`, `confirmed_at`, actual `response_ref/response_text`, `summary_event_ref`, `response_event_ref`, and that `snapshot_sha256`. A reply containing corrections returns to discovery rather than approving the old summary.
4. Run `<qa-tool> validate-requirement-readiness <context> --confirmed`. Only then derive/freeze coverage and render a reviewed XMind. Freezing and XMind rendering, including `--draft`, enforce the confirmed requirement gate.

The requirement digest covers sources, current understanding, decisions/history, visible question/answer events, branch reviews, business facts and pending questions. It excludes final summary/confirmation events (which reference it) and later test derivations. Changes invalidate readiness/confirmation and downstream baselines. Retain historical exchanges; add a new summary and actual confirmation after affected business changes. Do not replay unaffected questions.

Legacy baselines lack this evidence. Reuse verifiable facts and real exchanges if available; review unclear claims and confirm a current consolidated summary. Never just upgrade version numbers, synthesize old dialogue or add approval text to pass validation.
