# Wewo QA Case Executor

Consume the confirmed XMind/Excel baseline, inspect the actual project code and testing infrastructure, reuse or generate maintainable automated acceptance tests, execute them against the identified test environment, and deliver `test-execution-report.xlsx` with native evidence. Writing code is not completion; the code must run.

## Scope

- Expected behavior comes from the confirmed requirements and cases. Source code resolves selectors, interfaces, existing helpers, test runners and execution seams; it cannot redefine correct behavior.
- Modify test code, fixtures, page objects and necessary test-only configuration. Record product defects; do not fix production implementation or weaken assertions to obtain a pass.
- Preserve the case's evidence surface. A UI-visible oracle needs real UI execution. An interface-defined oracle may use an acceptance API test. Mocked or unit-only results cannot stand in for a deployed cross-module business flow.
- Use the project's established framework and dependency setup. The bundled artifact helper needs no tester-installed language runtime; generated project tests use the existing/agent-provided project test runtime. If indispensable infrastructure is unavailable, record the actual blocker; do not promise execution without it.

## Workflow

1. Resolve the [bundled runtime](../runtime-tool.md). Validate the requirement/point/case baselines and **all three Excel views**, then select the requested suite and targets. Import and review any Excel edits before running. Before writing code, walk each selected case from preparation and data through ordered steps to every target-applicable `AS-*`; verify the source/rule/leaf links, expected value, business observation surface and cleanup. A missing business oracle or an unconfirmed rule returns to Designer for review; only record IDs, locators and environment-specific setup may be resolved here.
2. Inspect the actual product repository: applicable instructions, revision, relevant implementation, existing tests, dependency manifests/lockfiles, scripts/config, fixtures, helpers, reporters and deployment context. Verify that the inspected code and test environment correspond to the intended build. Ask once for remaining missing repository/environment/account/data inputs; continue independent readiness checks. Product code is required for this requested code-generation route, not for the Designer.
3. Prepare/freeze the [execution profile](references/execution-policy.md), reviewed manifest and selected suite workbook. Resolve safe data preparation, isolation/reset, credentials by safe references and cleanup. Execute ready non-manual pairs; retain concrete blockers for other pairs.
4. Map each case-target and every `AS-*` assertion to a real test asset, native test identifier, route and runner, retaining separate checks when one journey covers several leaves. Reuse or extend suitable existing tests; otherwise write the minimal durable code in the project's normal test directories. Do not put automation source in the tester delivery root. Reuse mature frameworks instead of building a custom test runner. Read [native automation](references/native-automation.md).
5. Review generated tests against case steps and frozen expected values. Check real selectors/interface paths, independent test data, the complete assertion set, wait conditions and cleanup. Discover actual locators from code/live UI when needed. Avoid arbitrary sleeps, blanket mocks and guessed interfaces. Restore declared dependencies using the existing project tooling; any new framework must be justified by the available repository infrastructure.
6. Run the focused native tests, collect exit status, native report, assertion observations, screenshots/traces/logs as applicable, then run the selected suite and necessary regression. Use `run-native-tests` for supported native-report collection. Another established runner may be used through a narrowly scoped adapter preserving the same records. Live tool clicks can assist reconnaissance but do not replace execution of generated test code.
7. Attribute failures to product, test code/locator, data, environment or requirement conflict. Repair permitted test defects, preserve the initial failing attempt, and rerun only as needed. Do not hide retries or convert skipped/undiscovered tests into passed. Native test success alone cannot cover a missing planned assertion.
8. Produce one truthful result for every selected case-target. Verify both native runner status and all planned assertions against original observations, including interrupted checks. Deterministic checks are recomputed; visual/semantic checks retain objective judgment and original evidence. Read [result contract](references/result-contract.md) and [observation evidence](references/observation-evidence.md).
9. Validate results and generate the tester-facing Excel report. Link to the native report (HTML where supported), evidence and project test assets. Keep run JSON/raw technical files under `.qa-state/runs/`. Give counts, failed cases, concrete blockers, manual exclusions, tested build and residual scope. Zero executed automated cases cannot pass the automation gate.

Completion requires durable code, actual runner execution, preserved native evidence and a report of all selected pairs. Blocked/manual scope remains visible. A project test runtime or code repository being absent does not authorize changing the user's requested workflow into UI-only execution.
